# 模型接力 · dsh-model-failover

把 **已经接入 dsh 的全部模型**排成优先级队列，再把这个插件本身当成**一组「模型」**——
**一条队列就是模型选择器里的一个模型**。用户在模型选择里挑中哪条（默认那条叫
`默认模板`，也可以自己新建、改名），任务就按那条队列的顺序去跑：靠前的先上，不行就自动
往下换，直到任务跑完。

## 它解决什么

一个模型不能输出，往往是这几种：额度用尽、余额不足、key 失效、路由挂了、上游 5xx。
以前遇到这些，任务当场就断了。现在：

1. 先用**第一个**模型跑；
2. 它出问题 → 把**同一个请求原样**再发几次（默认 2 次，为了换掉背后那个坏账号），
   还是不行再补一句「继续」试一次；
3. 仍然不行 → 换**第二个**模型，这一跳补上「继续」，接着跑；
4. 依次往下，直到某个模型把任务跑完；
5. 某个模型今天在这个会话里出过这种问题 → **这个会话今天不再从它开始**，直接用排在它后面、
   已经验证过能用的那个（别的会话照常可以先用它）；
6. 到了**第二天设定时间**（默认 01:00，可改），隔离自动清空，重新从第一个开始试。

另外，**整轮**以失败告终、或被 token 上限截断时（模型自己没坏，只是这一轮没跑完），
插件会替你自动补一句「继续」接着做 —— 见下面的「DSH 异常」。

## 装好之后长什么样

**模型选择器里多出几条**（provider `model-failover`）——**一条队列就是模型选择器里的一个
模型**。默认那条叫 `默认模板`；你在设置页新建一个模板，模型选择器里就多一项，名字就是你
给模板起的名字。会话里选了哪条，那个会话就往那条队列上跑。

**设置 → 模型接力**（在「模型」那一节下面）。同一类设置放在一起，从上到下依次是：

| 区块 | 作用 |
| --- | --- |
| 今日状态 | 今天是哪天、距下次重置还有多久、当前起点、今天隔离了几个（重置时间就在这里） |
| 队列模板 | 一条模板一行：改名、切到哪条去编辑（`编辑`）、`测试连接`、新建、`✕` 删除（会先问一次）。条数不限，新建出来是空队列；卡片底部两颗按钮把模板存成一个 JSON 文件、或者从这样的文件读回来 |
| 「某模板」的队列 | 正在编辑的那条模板的候选清单，每行前面是今天的**失败/成功次数**、一个**并发上限**输入框、一个**思考强度**下拉框，按住整行拖到新位置就能排序，`✕` 移除；**右键任意位置弹小窗看/改该模型的上下文窗口**；下面一个**搜索框**，敲几个字就只剩名字命中的那些，点一下那一行就加进队尾 |
| 模型异常 | 总开关、同一个模型失败后重试几次、多久没输出算卡住、被限流后绕开多久、并发模型收工之后再歇几秒、按真正跑的那个模型记账（下面一行写着到底接管上没有）、全部隔离时要不要硬试。开着的时候，队列里的模型一直在后台自动接力 |
| DSH 异常 | 总开关、两种触发、**各自**的次数上限、每次失败后等多久再补（见下）。对整个 DSH 生效，不限于接力 |
| 外观 | 会话页「隔离队列」里显示哪些会话：子智能体的（默认关）、其他工作区的（默认开） |
| 事件日志 | 每次隔离/复活/轮换/限流冷却/自动补发都留一条；记不记、留多少条也在这里 |

**「测试连接」的结论会留到你刷新页面为止。** 一颗模板一颗按钮，点了就按顺序把你这条
队列里的模型各探一遍，通不通、几百毫秒，写在每个模型名字后面。探到一半切去看会话、去改
别的设置，都不要紧：探测照样跑完，切回来结论还在 —— 面板关掉不等于把体检叫停，也不会
因为换了个页面就从头再探一遍。悬停能看见这个结论是什么时候测的，所以隔了一阵再看到它时，
你心里有数它是新的还是旧的。

这份结论**不写进配置文件**：它是「刚才那一刻」的体检结果，存下来就成了永久结论 ——
账号掉了、额度用完了，它还理直气壮写着「通」。刷新页面清空它，那时候重测一遍是合理的。

**加模型：上面搜，下面点。** 队列下面那个框是搜索，不是下拉框。敲几个字，清单只剩名字里
带这几个字的那些（模型名、模型 id、路由名与它的中文名，四样都认，大小写无所谓）；
点任意一行就把它加进队尾，加完关键字自动清掉，接着找下一个。回车等于点第一行，`✕` 或
`Esc` 清空。**已经在队列里的模型不会再列出来**，所以清单里剩下的永远是可以加的。

搜不到时会说「没有名字里带『你搜的字』的模型」，而不是「没有扫到可用的模型」—— 那是目录
真的空着时才会有的说法，两者别混。关键字是空的、清单也空着的时候，它说的是第三种话：
「能加的模型都已经在队列里了」。

**账单记在谁名下。** 这条路由在模型选择器里叫「模型接力」，可真正跑的是队列里的某一个模型。
默认情况下宿主会把它记成一个叫 `model-failover:default` 的假模型 —— 一天下来那一行几百次
调用，点开看不出钱花在谁身上。现在账单记在**真正跑的那一个**身上，各按各的价算。

做法是接管宿主的计费入口（把 dsh-cost-meter 挂在全局的那座桥的 `createScope` 包一层），
不是伪造数据：外层这一次「模型接力」调用不再入账，内层那个真实候选自己作为一次独立调用落账。
这两件事必须成对 —— 只让外层不记会整单漏计，只让内层落账会一笔记两次。所以「外层不记」是
**有条件的**：这一趟真的见过内层的真实调用才生效；取不到桥、桥的形状变了、或者这一趟压根
没往下走（模板是空的），就原样退回旧行为 —— 宁可名字记错，也不漏记、不双记。

「内层这一笔属于哪一趟外层调用」这件事，凭据是**跟着那一次真实请求的参数一起走的**，不靠
异步上下文猜 —— 宿主怎么调度、中间隔了多少层，都认得出。

计费桥是 dsh-cost-meter 在它自己加载时挂上去的，谁先加载看插件顺序，所以本插件会在
`globalThis` 的那个位置上装一个**访问器**：桥什么时候来、被换掉、被删掉再重挂，都会被
顺手包好，不用等人再来装一次（另外启动后 0 / 200 / 500 / 1000 / 2000 / 4000 毫秒还会
各试一次，装上了日志里说一句）。每派发一次真实调用也顺手补一眼 —— 桥被 cost-meter
卸载又重装时，访问器会跟着一起消失，这一眼就是补它。

**接管上了没有，设置页那一行写着。** 开关下面那颗小标写着「已接管 / 没接管」，后面跟着
「这一进程：路由名调用 N 次，其中 M 次记到了真实模型名下」。以前这件事完全不可见：开关是
开的、界面照常跑、日志一片安静，只有翻账本才会发现整天都记在「模型接力」名下。三种情形
都看得出来 —— 还没接到桥（`没接管` + 在等什么）、正常（`已接管` + N/M）、以及最阴的一种：
接上了却一次都没落账（`已接管`，但会直接说「这些调用一次都没落到真实模型名下」并告诉
你下一步怎么做）。关掉这颗开关就不再提这些。

关掉这颗开关就回到旧行为；老配置里没这个键，也当作开着。

**费用卡上的名字也是同一个问题，但它走的是另一条路。** 会话里那条「本轮费用」不看账本，
它读的是**这一轮的事件流**：`assistant/message` 里那条消息的 `source.provider / source.model`。
宿主写这条消息时用的是外层请求的身份（也就是「模型接力」），所以账本改好了，卡片上仍旧是
`model-failover:default` —— 两件事互不相干，得分别修。

真正的候选藏在这条消息的 `source.replayState.response` 里（每次真实调用都会带回来），所以
本插件在**算钱的人**读会话事件时把名字换掉：`snapshotEvents / ownEvents / eventAt` 这三个出口
都一样，只换 `provider / model` 两个字段，`replayState` 和 `usage` 一个字节不动，原事件也不会
被改（它们是深冻结的，改了会炸）。没有 `replayState`、或者本来就是别的 provider 的消息，原样
过去 —— 不凭空编名字。

**只换给算钱的人，这一点是必须的。** 会话事件流不止一个读者：宿主自己也读它去落盘、去分叉
会话、去算每条消息的投影，拿到的要是换过名字的副本，等于把「模型接力」这个真实身份从持久
数据里悄悄抹掉。所以换名是有门禁的 —— 本插件把 `costMeter` 服务的每个方法包一层，只有在它的
方法里读会话时才挂上「正在算钱」的标记，其余任何时候 `sessions.get()` 给出去的都是原对象。

会话服务与费用服务都可能比本插件晚发布，所以这里也是一样：启动后各试几次，另外每次 `/state`
轮询补一眼；开关关了立刻回到宿主的原样，卸载时把两层包装都收回去。设置页在账单那一行下面还
多一颗小标：「费用卡已接管 / 没接管」—— 账单接上了不等于卡片接上了，分开写才不会互相背锅。
接管之后那颗标还会报个数（「这一进程换过 N 条回复的名字」），免得「装上了但一条都没换」被当成
正常。

一个已知边界：**只对开着的会话有效**。冷会话（进程里已经没有这个会话）cost-meter 是直接读
`$DSH_HOME/sessions` 下的 JSONL，那条路上插不进去，历史会话里仍旧是「模型接力」—— 这是有意
的取舍：宁可少改一处，也不去改宿主的磁盘格式。

**会话页「隔离队列」里那三档颜色是三种不同的处境。** 红的是今天在这个会话里坏过、已经
划进隔离名单的；绿的是今天验证过能用的；**黄的是被上游限流、正在冷却的** —— 它没坏，只是这
一会儿忙，几十秒后自己回队列，不算今天的隔离，明天也不用等重置。黄色那颗鼠标移上去会直接
报**「限流中，3 分 20 秒后恢复」**：剩余时间按你停上去的那一刻现算，所以不需要列表每秒重画
也能准，冷却表是**整台机器一份**、按模型算的，同一个模型在别的会话里也同时在等。

**把隔离划掉之后，下一趟就回队首。** 会话页上那颗 ✕ 把某几条隔离记录划掉的时候，正在跑的那
一趟**不打断** —— 用户手上正写着的半句话不该被从中间换个人接着写。等这一趟自己输出完，下一次
请求就**从队列第一个没被隔离的模型重新开始**，而不是继续在这个替补身上跑下去。

这里只认**排在我前面**的那几位：拿名额的时候他们被隔离着、现在被放出来了、而且位置在我前面，
就把座位还回去（**不带**收工冷却 —— 这一趟活还没干完，没理由让上游先歇）。划掉的是排在后面的
记录、或者划掉之后前面仍旧全被隔离，都不会动正在跑的这一趟 —— 那种时候换人纯属瞎折腾。
它也不跨会话：别的会话划名单不影响你这一趟的座位。

**上游报错不再直接弹到你脸上。** 早先有几类错误被当成「换谁都没用」，撞上就把整条队列
丢掉、把错误原样弹到会话页：一类是 `upstream` 那批（502、连接被重置、DNS 没解析出来、
超时），一类是上下文装不下。前一类本来就是这个插件存在的理由 —— 一个上游挂了，换下一个
就是了；现在它们也照样走「原样重发 → 换下一个候选」，只有你自己按了停止（`ABORTED`）
才立刻收手。

**「网线没通」和「话说到一半被掐断」是两件事，只有一个要救。** 请求根本没送出去（DNS 没
解析出来、代理没起来、证书被本机拦下）时，补一句「继续」只是往同一个坑里再扔一次，白烧
补发次数，所以那种失败**不**补发。但上游把话说到一半就把连接掐了（`Stream ended without
finish_reason` 这一类）恰恰相反：模型已经读到上下文、也开始写了，补一句「继续」它就能接着
写下去 —— 这种必须补。

麻烦在于这两件事**常常报同一个错误码**（`TRANSPORT`）：它既被拿去包住「请求没发出去」的
`fetch failed`，也被拿去表示「流没正常收尾」。所以判据不只看码，还看那句话本身：message
里出现 DNS / 连接 / 证书这些硬证据，就按本机网络处理；一句硬证据都没有、却点名了「没有
`finish_reason`」「ended without」「incomplete」这种收尾动作的，就按截断处理，照常补发。
两条都不沾的，仍按原来的口径算本机网络 —— 宁可漏判，不要误判。

**哪些失败算「忙一会儿」：认码、认协议、认写法，不认态度。** 一次限流和一次「这个模型今
天不行」在界面上完全是两种结局（黄一会儿 vs 红一整天），所以这一刀要切得准。下面这几类都
是**足够明确**的排队信号，一律只冷却、不进隔离名单：

- HTTP 状态码 `429`。协议层说的话，适配器给什么错误码都不改变这个事实；
- 码名里带 `rate_limit` / `throttle` 的，大小写和下划线都不计较 —— `RATE_LIMIT`、
  `rate_limit_exceeded`、`bili_throttle_hold`、`bili_throttle_terminal` 都算。最后两个是
  bili 出站闸门自己的码：上游在排队时它先攒着不发，到点自动放开（`hold`），连撞太多次就
  干脆歇一会儿（`terminal`）—— 文案里未必再复述一遍 `rate-limited`，光看码就该认出来；
- 报错文本里的 `rate limit` / `rate-limited` / `rate_limit_error` / `throttled` /
  `Too Many Requests` / `429`，以及 `concurrency limit`（Anthropic 与不少中转说「账号并发
  满了」就是这么写的）；
- gRPC 的 `RESOURCE_EXHAUSTED`（就是 429 的等价物），以及结构化字段里的
  `"type":"overloaded_error"`。

反过来，**裸的 `overloaded` / `capacity full` 故意不收**。线上真正见到的写法是 Cloudflare
的 502/504 说明页，正文写着「the origin is overloaded or misconfigured」，那是网关坏了；
还有中转自报的「system disk overloaded (99.1%)」。按裸词收下来，等于把所有 5xx 都改成冷
却，隔离名单形同虚设 —— 宁可漏判，不要误判。

**上下文装不下：先找窗口更大的接着写，实在没有才交回宿主压缩。** 队里某个候选的窗口装
不下这一轮，就把这一轮交给排在后面、**窗口更大**的那个候选接着写 —— 上下文一字不动，用户
看到的就是「它继续说」，而不是「会话弹个错然后什么都得重新来」。换人这件事只在事件日志
里留一条 `overflow-relay`，**不进隔离名单**：窗口小不是「今天坏了」，明天它一样能用。
队里一个更大的窗口都没有时，才把这个码交给宿主 —— 那是唯一认得它、也唯一会去压缩会话
再重试的一方（压缩会砍掉上下文，所以它只能是最后一步，不能是第一步）。

判定「这一坨太大」靠的是上游的原话。像 `body too large` 这种词，只有在同一句里还提到
context/token 才算数：线上真实的 codearts 401 原话是「Incorrect IAM authentication
information: calc ak sk signature fail:body too large」，那是坏凭证，跟上下文毫无关系；
被误判成超长之后它绕开了隔离与换人，一整天都在同一个坏凭证上打转。

**连着撞输出上限的模型，攒够两次就进隔离名单。** 撞上限本身不是「这个模型坏了」，它只是
还没写完，所以第一次照旧让它接着写。但同一个模型在一个会话里连着撞两次，说明这一轮它写
不完 —— 再惯着它只会让同一句半截话被反复截断。攒够就记进当日隔离名单（错误码
`MAX_TOKENS_STREAK`，事件日志里一条 `ceiling-streak`），**这个会话今天不再从它开始**，
直接用下一个模型接手。别处会话照样可以用它：它在别人那儿也许只是话多。

**注意：** 不同的模型（包括量化版与蒸馏版）混用可能会导致缓存命中率大幅下降，请尽量把同一模型安排在同一队列，即使是dsv41flash的0910版本和1017版本都有区别。
